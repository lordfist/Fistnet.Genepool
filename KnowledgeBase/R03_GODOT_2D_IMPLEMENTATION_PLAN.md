**Proposed result and architecture**

Add `Fistnet.Genepool.Godot` to the existing root `Fistnet.Genepool.sln`. It will be a complete alternate application: the familiar 100×100 board, food, organism details, statistics and playback/settings controls in a Godot window. It directly references the existing Control library, which references Dna. One existing `SimulationRunner` owns one simulation inside that application; Godot receives detached `ViewFrame` snapshots and sends explicit commands. No process communication or WinForms window embedding is needed.

The existing WinForms application remains a usable startup project and comparison viewer. Starting both applications would create independent worlds, not two views of one running world. This plan preserves simulation rules, random draws and default setup. The later 3D step can reuse the same simulation connection, identities, commands and much of the UI, but will require its own scene, camera and picking implementation.

**3. Implementation steps and checkpoints**

1. **Establish the toolchain with a minimal window.** After approval, obtain and verify the editor, configure the local package feed/cache, create the new project and add it to the root solution. Build the whole solution in Debug and Release using VS2022 MSBuild. Verify the SDK actually selected despite build-helper environment overrides, plus referenced-library configurations during direct ExportRelease compilation. Set Godot's external editor to Visual Studio and establish the VS2022 executable launch profile. Launch a visible empty Compatibility-rendered scene, record renderer/adapter information and reject a software fallback as GPU evidence. Check launching both startup choices. If this integration fails, resolve that specific problem before constructing the full viewer; do not silently change the solution's framework or Visual Studio requirement.

2. **Build the board against fixed snapshots.** Create a clipped SubViewport for the board with Node2D and Camera2D, so zoom/pan cannot cover controls. Use one board unit per cell, with fit-to-board, wheel zoom and drag pan. Use two MultiMeshInstance2D batches: food tiles and organism tiles, with reusable quad meshes and instance buffers sized for the 10,000 cells. Food colors and organism DNA colors follow the current palette. Combined mode leaves food visible around the smaller organism tile; Organisms and Food modes preserve current meanings. Selected cells, markers and trails use a small separate overlay. Validate several fixed fixtures before connecting a live world.

3. **Connect the existing simulation worker.** Create one SimulationRunner in the application, await its readiness and consume LatestFrame on Godot's main thread. Upload changed snapshots at the existing bounded publication cadence; keep no growing frame queue. Detect a new frame object/run identity and command acknowledgment, not just season number, because selection or command state can change within one season. Access no mutable Board state from rendering. Keep Godot scene/resource mutations on its main thread, and close using asynchronous StopAsync while the UI continues responding. Surface worker faults. [Godot threading constraints](https://docs.godotengine.org/en/stable/tutorials/performance/thread_safe_apis.html).

4. **Port the useful viewer controls.** Provide Run, Pause, Step one season, full eight-season cycle, Restart, New Simulation and the existing speed choices. Include Combined/Organisms/Food layers, Fit, pattern highlighting/dimming, selected-organism details, activity and history views, and trail/marker/history toggles. Preserve explained pattern groupings, food scales, selected history limitations, setup presets and all existing settings fields. New random worlds remain the default; Restart retains the current setup/seed. Carry through non-visible policy/execution options when the settings form is edited. Selection uses the displayed frame's stable organism ID, transformed camera coordinates and checked board boundaries. Show actual seasons/second, requested speed and pending command state distinctly.

5. **Keep rendering smooth without changing simulation speed.** Process camera and UI interaction at the display rate, aiming for 60 Hz with normal VSync. Rebuild data only for new snapshots, generally no more than the producer's approximately 10 Hz during fast running. Submit packed transforms/colors in bulk and reuse buffers; do not create one updating Godot node or physics body per organism. Do not invent movements between skipped simulation snapshots in this first view. Long simulation calculations may still delay the next completed season, but should not freeze camera, controls or presentation. [MultiMeshInstance2D](https://docs.godotengine.org/en/stable/classes/class_multimeshinstance2d.html), [MultiMesh buffer API](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html#class-renderingserver-method-multimesh-set-buffer).

6. **Verify behavior, integration and actual graphics.** Run the existing test suite in Debug and Release; the last verified baseline is 137/137 in each, not a fresh result from this planning turn. Add targeted tests for palette boundaries, transformed picking, settings preservation, reset/selection identity and command acknowledgment. Use a small built-in C# verification scene for Godot-specific checks rather than adding another test framework. Headless checks cover imports and logic only. A real window must verify GPU rendering, representative food/organism layers, selection after pan/zoom/resize, settings, pending controls and shutdown. Compare fixed screenshots with tolerance for rendering differences; keep a small current review set.

7. **Measure the renderer independently and present the review.** Use fixed 0-, 1,000- and 10,000-organism fixtures, replaying fresh snapshots at 10 Hz without simulation computation. For each, use five seconds of warmup and ten seconds of sampling at a stated window size, then exercise a bounded live run. Proposed targets: aim for 60 FPS, with 95% of measured frame intervals at or below 33.3 ms at 1920×1080, and input acknowledgment within 100 ms; report command settlement separately. Test resize/layout at 1366×768 as well. Report actual backend, workload and timing limits rather than claiming presented-frame or GPU timings that were not measured. Use bounded deterministic replay/passivity checks, not another ecology evaluation. Finish with whole-solution VS2022 builds, regression results, launch instructions and owner review of the familiar GPU view. Stop before R03's depth/3D and graphics-polish steps.

These timing targets are proposed review criteria, not achieved results or owner-approved requirements. A renderer failure should lead to a specific local fix and repeat of the affected check. A fundamental integration or hardware limit should be reported before a change of design. The existing WinForms startup option provides a usable comparison throughout.

**Expected development workflow**

Open the same root `Fistnet.Genepool.sln` in VS2022. Select **Debug**, the new Godot project and its generated executable launch profile, build, and use F5 to start the viewer. Use Godot's editor for scene/UI editing, with Visual Studio as its C# editor. The application runs through Godot's executable; a built C# library is not a standalone `dotnet run` application. Release/ExportRelease compilation is verified separately; ordinary editor launching is not claimed to execute the ExportRelease assembly. Exported Release runtime verification belongs to the later packaging checkpoint.

Future launch commands use the verified extracted executable with `--editor --path <Godot project>` for scene editing, or `--path <Godot project>` to run. Add `--rendering-method gl_compatibility` explicitly. Headless `--path <Godot project> --import` checks imports. These are planned command forms; no command has been executed for this plan. [Godot command-line reference](https://docs.godotengine.org/en/4.7/tutorials/editor/command_line_tutorial.html).

When standalone packaging is requested, install matching .NET Windows export templates, define a Windows x64 export preset and invoke Godot `--headless --path <project> --export-release "Windows Desktop" <absolute output exe>`. Create the output directory first. Its managed publish uses ExportRelease, win-x64 and self-contained deployment; required .NET runtime packs may also restore through NuGet. `dotnet publish` alone does not assemble a complete Godot application. Packaging, template download and exported-runtime verification are deliberately deferred from the first development viewer milestone. [Export workflow](https://docs.godotengine.org/en/4.7/tutorials/export/exporting_projects.html), [versioned publish implementation](https://github.com/godotengine/godot/blob/4.7.2-stable/modules/mono/editor/GodotTools/GodotTools/Build/BuildSystem.cs).
